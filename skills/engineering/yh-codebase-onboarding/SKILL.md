# 摸清陌生代码库（yh-codebase-onboarding）

为"刚拿到一个陌生项目、马上要在它上面用 Claude Code 改代码"的**决策者**，建立一份可落盘、可扫读的**心智模型**。你负责理解与下指令，Claude Code 负责执行——所以这份文档只装**你需要懂的**，不下到行级代码细节。

## 适用场景

- 第一次打开一个项目，想快速建立"它是什么、怎么跑、边界在哪"的整体认知
- 接手别人的 repo、加入新团队
- 用户说"摸清 / 上手 / 带我过一遍 / 帮我理解这个项目 / 梳理外部依赖"

## 核心原则

1. **单一产物，单一读者** — 只产出 `docs/onboarding.md`，给**人（你）**读，用来建立心智模型。**不碰 CLAUDE.md、不产出给 AI 的护栏**——那是下游 skill 的职责。
2. **过滤器：只留 AI 查不到的** — 每写一行都问："这提高了我对『系统做什么、为什么』的理解吗？" 凡是 Claude Code 自己能现查的，一律不写——既会过期、又零增量。

   | Claude 能现查（**不写**） | Claude 查不到、得你沉淀（**写**） |
   |---|---|
   | 某功能在哪个文件、调用关系 | 系统**为谁解决什么问题** |
   | 命名风格、错误处理模式 | 哪些是**核心场景**、哪些是边角 |
   | 用了什么框架/库（看 manifest） | 业务**不变量**、状态机 |
   | 目录结构 | 改 A 必带改 B 的**隐式耦合**、危险区 |
   | | 依赖哪些**第三方服务**、挂了会怎样 |

3. **从行为信号侦察，不从构建工具链** — 路由表、DB schema、测试名、README、commit 揭示"系统做什么"；eslint/tsconfig/Makefile 只揭示"怎么配环境"，不是重点。
4. **画出来** — 架构与数据流用 **ASCII**（终端不渲染 Mermaid，一律 ASCII art）。
5. **服务 ≠ 库** — 梳理外部依赖时只抓**跨网络边界的第三方服务**（Stripe / Anthropic / SendGrid），不抓进程内的库（`lodash`、`axios` 本身）。`axios` 不是依赖，它打到的那个 `api.stripe.com` 才是。
6. **标记缺口与推断** — "无法确定""这是推断"比编一个错答案有用。没有外部依赖就如实写"无"，绝不为填表硬凑。

## 工作流

默认**连续推进**，只在三个关键点停下对齐：① 用途+技术栈　② 心智模型　③ 落点。

### Phase 1 · 侦察（并行采集**行为信号**）

并行跑，不逐文件 Read：

```
1. 语言/框架     包管理清单：package.json / go.mod / Cargo.toml /
                pyproject.toml / pom.xml / Gemfile / composer.json
2. 能力面        路由表 / API 端点 / handler / CLI 子命令  → 系统"能做什么"
3. 领域名词      DB schema / migration / model 定义        → 实体与约束
4. 业务规则金矿   测试名（如 "should reject order when inventory is zero"
                用大白话写明了"本该如何"，不读实现就能提取不变量）
5. 意图          README / docs / 用户可见文案
6. 结构          入口点（main/index/app/server/cmd）+ 目录树顶 2 层
                （忽略 node_modules/.git/dist/build/.next/vendor）
7. 外部依赖(若有) .env.example 的密钥名（STRIPE_SECRET_KEY / OPENAI_API_KEY /
                *_API_URL）、manifest 里的 SDK 包（stripe / @anthropic-ai/sdk /
                twilio / @aws-sdk/* / googleapis）、HTTP client 调用点的 base URL、
                webhook handler（谁回调你）、docker-compose services（redis/
                postgres/kafka）、OAuth/登录配置
8. 近期动向      git log --oneline -30  → 最近在动什么、什么重要
```

### ★ 检查点 1 · 确认用途 + 技术栈

把**"这个项目做什么 + 检测到的技术栈"**简明列出，停下来问：

> "我判断这是 [为谁解决什么] 的项目，技术栈是 [语言/框架/DB/架构]。对吗？有要修正或补充的吗？"

**误判用途和误判技术栈一样致命**，会让后面全废，所以这里必停。

### Phase 2 · 建立心智模型（连续产出文档各节）

按下方文档结构逐节产出。两节是重头：

- **核心流程** — 挑这个产品最重要的 **1~3 条主干**，当故事**端到端**讲一遍：只讲概念层的关键决策点和状态流转，**不下到行级**。判据："搞懂这 3 件事 ≈ 懂了 80% 的系统行为"。
- **架构** — 重心是**模块边界 + 模块间通信契约（REST / 事件 / 直接调用 / 共享 DB）+ 危险耦合区（改 A 必带改 B）**。外部依赖就是图里"射出去的边"。

### ★ 检查点 2 · 心智模型对齐

架构 + 领域模型 + 核心流程讲完后，问一句：

> "这跟你的心智模型对得上吗？想深挖哪块？"

这是理解结晶的时刻；**大仓 / monorepo 也在此收口**——让用户挑一个切片深入，别试图把整个海煮开。

### ★ 检查点 3 · 确认落点并写入

- 默认写入 `docs/onboarding.md`，写入前确认路径（可改到别处），`docs/` 不存在则创建。
- **写入前先查落点是否被 gitignore**：`git check-ignore <落点>`。命中则提示"该路径不进版本控制，团队看不到"，并给选项：换到不被忽略的位置（如项目根 `ONBOARDING.md`）、`git add -f` 强制纳入、或接受只作本地参考。
- 终端只回一段简短摘要 + 文件路径，完整内容在文件里。

## 导览文档结构（写入 docs/onboarding.md）

```markdown
# Onboarding: <项目名>

## 一句话定位
[为谁、解决什么问题。一句话讲清这个产品的存在理由]

## 功能场景图
| 角色 | 核心场景 | 主要涉及模块 | 证据 |
| 买家 | 下单→支付→收货 | order/ payment/ | routes 表 + 下单测试 |
| 卖家 | 上架→改库存→发货 | product/ inventory/ | ... |

## 核心领域模型
[实体 + 不变量 + 状态机，例：]
- Order：状态机 draft→paid→shipped→completed，不可逆
- Product：soft delete，已下单商品不能物理删除

## 核心流程（1~3 条主干，端到端，概念层）
[挑最重要的流程，当故事讲一遍关键决策点与状态流转，不下到行级]

## 架构
[ASCII 图：模块边界 + 通信契约 + 危险耦合区。第三方依赖画成射出去的边]

## 外部依赖（第三方 API / 服务）  ← 条件性：无则写"无外部依赖"
| 服务 | 提供什么能力 | 用在哪条流程/场景 | 关键度 & 挂了会怎样 | 密钥/配置 |
| Stripe | 支付 | 结账主链路 | 硬依赖，挂=无法下单 | STRIPE_SECRET_KEY |
| Anthropic | AI 摘要 | "智能总结"功能 | 可降级，挂=该功能不可用，主站正常 | ANTHROPIC_API_KEY |
（另记一行：自建基础设施 Postgres/Redis/Kafka；同组织的内部微服务）

## 操作手册
[怎么跑起来 / 怎么跑测试 / 怎么部署——只记**非显然**的步骤与坑]

## 未解明 & 推断
[哪些是猜的、哪些没法确认，如：关键度为推断；测试框架无法确定]
```

**外部依赖表的灵魂是"用在哪条流程"和"挂了会怎样"**——前者把依赖挂回你的场景图，后者是纯读代码看不出、却最影响系统行为的那层（除非有明确的 fallback / circuit breaker 佐证，否则标明是推断）。列太挤可砍，但这两列别省。

## 反模式（不要做）

- **下到行级代码细节 / 报文件行号** — 这是给人建心智模型，不是代码地图；具体文件让 Claude 现查。
- **抄 manifest、列举所有依赖** — 只点出**塑造系统行为与边界**的那几个。
- **把命名约定、错误处理风格当重点** — Claude 看俩邻居文件就学会，对"理解"零增量。
- **改 CLAUDE.md 或产出给 AI 的护栏** — 越界了，那是下游 skill 的活，本 skill 不碰。
- **画泛泛的"请求生命周期"模板图** — 要画**这个项目**真实的 1~3 条主干流程。
- **用 Mermaid** — 终端不渲染，一律 ASCII。
- **编造外部依赖的关键度/失败模式** — 没依据就标"推断"或"未确认"；没依赖就写"无"。
- **跳过检查点一口气写完** — 用途、心智模型、落点三处必须对齐。
- 照抄 README — 导览要补 README 缺的**结构性洞察**，不是复述。
